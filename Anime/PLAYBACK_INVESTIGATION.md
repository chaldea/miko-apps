# 媒体访问与网络出口排查

本次复测日志日期：2026-11-10（北京时间）。

同一个 MP4 URL 在直连出口发生 TLS 连接重置，更换出口后返回有效数据，说明媒体文件在当次测试中仍然可用。这个对照尚不能区分 IP 限制、地域或线路限制、中间网络设备干预，也不能确定首次触发条件。

## 网络对照

所有媒体探测均使用 `Range: bytes=0-4095`、`User-Agent: libmpv`，最多读取 4096 字节。这里的 User-Agent 仅为诊断参数，不代表应用原生播放器实际发送的请求头。探测未添加 Referer、Cookie 或媒体 Authorization，也未执行批量分集请求或自动重试。

| 路径 | 观察 | 结果 |
| --- | --- | --- |
| 显式直连 | 不使用系统 HTTP 代理 | TLS 连接重置，未收到 HTTP 响应 |
| `127.0.0.1:7890` | 日志显示目标域名命中直连规则，最终为 `DIRECT` | TLS EOF；实际出口未改变 |
| 临时独立代理 | 出口检测与媒体域名日志确认使用不同出口 | 旧 URL 返回 `206`、`video/mp4`、4096 字节，包含有效 MP4 文件头 |
| 同一临时代理重新登录、获取详情、解析分集 | 解析结果与旧 URL 相同 | 解析成功，媒体同样返回 `206` 和有效 MP4 文件头 |

旧 URL 在重新登录和解析前已成功读取，说明这次恢复访问无需刷新播放地址。临时代理仅供诊断进程使用，绑定回环地址，测试结束后已停止并删除配置；系统代理及日常分流规则保持原状。

## 应用侧行为

- API 请求和媒体传输使用不同的网络路径。Miko 的 Android/Windows 视频传输由平台原生播放器处理，为 API 客户端的 `HttpClient` 配置代理不会自动改变媒体连接的路由。
- 当前应用通过 Miko 调用 Windows Media Foundation 和 Android MediaPlayer。不同传输实现可能具有不同的 HTTP/TLS 行为，但本次没有证据将某种客户端特征认定为限制原因。
- 图片源所需的 Referer 和浏览器 User-Agent 仅用于对应图片域名。此次媒体对照在没有这些请求头的条件下成功，不能将图片请求配置直接套用到视频服务。
- `DetailContent.Resolve()` 在加载、手动选集、换线路或重试时解析一次；`AsyncPage.Run()` 阻止忙碌期间重入。应用与 Miko 会话代码在错误后没有自动循环重新解析或加载。平台播放器内部仍可能产生 Range 请求或重试，本次没有记录其完整网络行为。

本次排查未调整播放等待时间、媒体请求头或解码器。进一步确定服务端限制规则，需要对应出口、时间与域名的 CDN/WAF 日志。

## 验证范围与记录

此次确认了播放地址解析和媒体文件头读取，尚未完成受影响媒体在应用内的全片播放验证。若要通过代理恢复原生播放，需要确认媒体连接实际使用可用出口；仅配置 API 请求的代理不足以验证这一点。

诊断输出位于 Git 忽略的 `Anime/artifacts/antileech-check/`：

- `initial-probe.json`：直连及本地代理端口的初始失败记录。
- `isolated-proxy-result.json`：出口差异、旧地址的 206 响应与媒体域名路由。
- `fresh-proxy-result.json`：重新登录、解析后的地址与读取结果。
- `resolve/`：调用当前应用 API 客户端的单分集 C# 诊断程序；当次构建为 0 警告、0 错误。

本说明不包含账号密码、会话令牌或代理凭据。
